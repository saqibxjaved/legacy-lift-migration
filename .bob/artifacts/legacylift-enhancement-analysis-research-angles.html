2. Five Ranked Enhancements — Pick One to Publish

Ranked by: research novelty × implementation feasibility × challenge score impact

1 True Parallel Subagent Execution with Convergence Gating Highest Research Value
Workflow: Application Maintenance & Code Review · Bob feature: spawn_subagent · Difficulty: Medium

The problem today: All three agents (Architecture, Security, Testing) run sequentially inside one context. On a real 50-class monolith this means one agent's token budget crowds out another's. Sequential also means ~3× slower — if each agent takes 2 minutes, that's 6 minutes vs 2 minutes in parallel.

The enhancement: Replace the three prompt-file agents with true spawn_subagent calls that run in genuinely isolated contexts simultaneously. Bob's parent waits for all three to return, then applies a Convergence Gate — it only proceeds to migration if:

  • Architecture Agent: no circular dependencies flagged as BLOCKER
  • Security Agent: no P0/P1 findings (or user explicitly overrides)
  • Testing Agent: baseline test pass rate ≥ 60%

Why this is publishable: You can measure and report concrete wall-clock time: "3 parallel subagents completed in 2.1 min vs 6.3 min sequential — 3× speedup." That is a hard, reproducible number. You can also show that the convergence gate blocked a migration that would have carried a SQL injection vulnerability — demonstrating error prevention, not just automation.

2 Document Understanding: Ingest pom.xml, Javadoc & Architecture Decision Records Directly addresses challenge gap
Workflow: Onboarding + Application Maintenance · Bob feature: Document Understanding · Difficulty: Low–Medium

The problem today: The pipeline reads Java source code only. It has zero awareness of: what the project intends to do (ADRs), what libraries it depends on (pom.xml / build.gradle), or the business context written in Javadoc. A migration that ignores these produces technically correct but contextually wrong microservices — e.g., splitting a class that an ADR explicitly says must stay monolithic for performance reasons.

The enhancement: Add a Document Ingestion Stage (Stage 0.5) that uses Bob's document understanding to parse:

  • pom.xml / build.gradle — extract dependency versions, flag CVEs, map library → Python/TS equivalent
  • Javadoc comments — extract business intent per method, carry it into migrated docstrings
  • Architecture Decision Records (.md files) — identify "do not split" or "must be async" constraints
  • README / Wiki (.docx/.pdf) — feed onboarding context to the Architecture Agent

Why this is publishable: This directly demonstrates Bob's unique "document understanding" capability — something no standard code migration tool does. The research angle is: "How much does ambient documentation context improve migration correctness?" You can compare migrated code quality with and without document ingestion as a controlled experiment.

3 Automated CI/CD Pipeline Generation (Release & Deployment Workflow) Highest challenge alignment
Workflow: Release & Deployment · Bob feature: Agent mode + file generation · Difficulty: Low

The problem today: After migration, a developer still manually writes: Dockerfile, GitHub Actions workflow, docker-compose.yml, and Kubernetes manifests. This typically takes 2–4 hours per microservice and is a major source of deployment errors (wrong port, missing env vars, no health checks).

The enhancement: Add a Stage 4 — Deployment Generation that, after successful validation, automatically generates:

  • Dockerfile — based on detected language, dependencies from requirements.txt/package.json
  • .github/workflows/ci.yml — runs the exact same test suite that passed in Stage 2
  • docker-compose.yml — wires together all migrated microservices with correct port mappings
  • k8s/deployment.yaml — basic Kubernetes manifest with resource limits derived from metrics

Why this is publishable: The complete workflow from "legacy Java file" to "deployable microservice with CI/CD" is a compelling, demo-able end-to-end story. You can show the exact files generated and run docker build to prove they work. This directly addresses "release and deployment processes" — a named workflow in the challenge.

4 Developer Onboarding Agent — Codebase Q&A + Runbook Generation Strong narrative for article
Workflow: Onboarding · Bob feature: Agent mode + document understanding · Difficulty: Low

The problem today: A new developer joining a legacy Java project typically spends 2–5 days reading code before they can make their first change safely. There is no interactive way to ask "why does UserService validate email this way?" or "which classes am I allowed to change without breaking OrderProcessor?"

The enhancement: Add an Onboarding Agent mode that, given the Modernization Report + source code + any uploaded docs (Confluence exports, README.pdf), can answer:

  • "What does this class do and why?" — from Javadoc + ADRs
  • "What breaks if I change this method?" — from dependency scan
  • "Where should I add a new payment method?" — from architecture layering report
  • "What are the security rules I must follow?" — from security agent findings

It also auto-generates a Developer Runbook: a structured markdown guide covering setup, key classes, forbidden patterns, and test instructions — derived entirely from the existing codebase and reports.

Why this is publishable: Onboarding is one of the most measurable developer workflows. Survey data consistently shows 2–5 day ramp times. You can construct a simple before/after: "without the agent, answer these 10 questions about the codebase; with it, answer the same 10." Time and accuracy are measurable.

5 Measured Impact Dashboard — Quantified Productivity Evidence Required for credibility
Workflow: All · Bob feature: report generation · Difficulty: Very Low · Should be done regardless

The problem today: The challenge explicitly asks to "clearly demonstrate impact." Right now the system produces a Modernization Report with before/after LOC and test rates, but there is no baseline comparison: how long would a developer have done this manually?

The enhancement: Add a productivity evidence layer that captures and reports:

  • Wall-clock time — timestamp every stage start/end in the pipeline; report total automated time
  • Industry baseline — cite published data: manual Java→Python migration averages 2–3 days per KLOC (from IBM, McKinsey, Gartner reports)
  • Error prevention count — number of static analysis issues caught automatically vs. what would have been manual review
  • Test coverage delta — tests existed before migration vs. tests generated automatically (count + coverage %)
  • Rework prevention — number of times the retry loop caught and fixed a migration failure without human intervention

Why this is essential: Without this, reviewers will say "interesting prototype, but where's the evidence?" With it, you can write sentences like: "LegacyLift migrated 3 classes, generated 35 tests, and caught 2 security issues in 4.2 minutes. Manual equivalent: estimated 14 hours." That is a publishable claim.

5. Three Known Weaknesses to Fix Before Publishing

WeaknessWhy It MattersFix
parse_java_ast uses regex, not a real parser Reviewers will call this out. Fails on generics, annotations, inner classes. Add a note in the paper that this is intentional (no JVM dependency) and list the known edge cases explicitly.
compare_behavior requires manual output capture The "behavioral validation" claim is weakened if you can't actually run the Java program to get its output. Add a run_java_program MCP tool that compiles + runs Java via javac/java if JDK available, or marks as SKIPPED.
No .bob/mcp.json — MCP server is not connected to Bob The demo can't actually run end-to-end inside Bob without this file. Create .bob/mcp.json with the legacylift-mcp server config. Takes 2 minutes.
